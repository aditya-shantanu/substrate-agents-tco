What does one agent cost per month on GKE with Substrate?

Substrate lets many mostly-idle agents share a few machines: an idle agent is suspended to a snapshot in cloud storage, and woken (resumed) when a request arrives. Set the assumptions on the left; the right side shows the resulting monthly bill and bill ÷ number of agents. Two sandbox types side by side: gVisor (any machine) and microVM (needs nested virtualization → Intel N1/N2/N4/C2/C3/C4 or N4D, GKE Standard only, ~10% CPU tax). Math: docs/MODEL.md · sources: prices, substrate, workloads, measured OpenClaw run. LLM token costs are not included.

1 · How busy is one agent?

A personal agent (OpenClaw, Hermes) mostly sleeps: a few chats plus some scheduled check-ins per day.

2 · How fast are suspend and resume?

While an agent is being suspended or resumed, its machine slot is busy but useless — that time is pure overhead added to every wake-up. These numbers depend on the agent (snapshot size, process thaw), not just on Substrate — re-measure for your workload (Phase 2).

Default = measured on a real OpenClaw agent on Substrate (2026-09-14, GKE): suspend 2.2 s, resume 3.4 s P50, 55–61 MiB snapshot — most of that is the Node.js process thawing, not Substrate (gVisor restore itself: ~0.2 s). Small glutton test actors measure suspend ≈0.4 s / resume ≈0.24 s. microVM values are estimates until measured.

s
How long the auto-suspend service waits after the last request before suspending. Protects multi-message conversations from suspend-thrash, but the wait itself occupies the worker on every wake-up. The OpenClaw demo ran an aggressive 2 s; its measured occupancy per cron wake was 8.3 s total (work + wait + suspend).

3 · Safety margins

You can't pack machines 100% full and still wake agents instantly, and evenings are busier than 4am.

×
0.7 = keep 30% headroom so a waking agent finds a free worker fast (the router only holds a request 5 s by default).
×
Capacity is bought for the busiest moment, not the average. The measured OpenClaw fleet model saw a P99 peak ≈3× the mean at 1,000 agents (random schedules); big fleets smooth this out, aligned cron schedules make it far worse. Use ~1 if the pool autoscales through the day.
/min
0 = no cap. Caps churn per worker (snapshot I/O, GCS traffic, node pressure grow with cycle rate). Applied at the peak hour: if agents wake often enough to hit it, each worker hosts fewer agents than time-sharing alone would allow, and cost rises. Each worker's hard physical ceiling is shown in the churn tile.

All intermediate numbers (everything the charts and tiles show, as a table)

The model: each wake-up occupies a worker for (useful time + idle wait + suspend + resume). Agents per worker = target utilization ÷ (per-agent occupancy × peak ratio). This is the same identity as the benchmarking formula QPS = workers ÷ (live + suspend + resume), inverted. Assumes one live agent per worker (Substrate today); multi-actor workers would raise density further.
